# 利用ガイド

[READMEに戻る](../README.md)

このガイドでは、リポジトリのセットアップから、F5による拡張機能の起動、検索、開発時の確認までを説明します。

## 必要なもの

- VS Code
- Node.jsとnpm
- Git
- `uv`（Python環境のセットアップに使用）
- 初回にパッケージや検索モデルをダウンロードするためのインターネット接続と空き容量

Python環境とPyTorchは拡張機能の `Setup / Start` から導入できます。通常のローカル検索にGemini APIキーは不要です。翻訳・クエリ拡張・Agentic検索を使う場合のみ設定します。

## F5で起動して試す

### 1. 拡張機能のプロジェクトを開く

このリポジトリをクローンし、`package.json` がある **OwlDiffSearchのルートフォルダ**をVS Codeで開きます。ファイル単体ではなくフォルダとして開いてください。

VS Codeのターミナルで、次を実行します。

```powershell
npm ci --include=dev
```

`node_modules` はGitに含まれないため、クローン後はこのインストールが必要です。依存関係を更新した後も同じコマンドで `package-lock.json` に記録されたバージョンをインストールできます。

### 2. F5で開発用ウィンドウを起動する

OwlDiffSearchのソースを開いているVS Codeで、サイドバーの「実行とデバッグ」から `Run Extension` を選び、緑色の再生ボタンを押します。「実行とデバッグ」はWindows / Linuxでは `Ctrl+Shift+D`、Macでは `Cmd+Shift+D` で開けます。

キーボードから起動する場合は、次の操作でも実行できます。

- **Windows / Linux**：`F5` を押します。
- **Mac**：`F5` を押します。音声入力などMac側の機能が動く場合は、`Fn`（地球儀キー）を押しながら `F5` を押してください。ファンクションキーの設定やキーボードによって操作が異なるため、うまくいかない場合は上記の再生ボタンから起動できます。

`.vscode/launch.json` と `.vscode/tasks.json` の設定によって `npm run watch` が自動実行され、コンパイル後に **Extension Development Host** という別ウィンドウが開きます。手動でwatchを起動しておく必要はありません。

- 元のウィンドウ：OwlDiffSearchのソース編集・デバッグ用
- Extension Development Host：拡張機能を操作して検索するためのウィンドウ

### 3. 検索するGitリポジトリを開く

**Extension Development Host側**で `File → Open Folder...` を選び、検索対象のGitリポジトリを開きます。最初はOwlDiffSearch自身を対象にしても構いません。

コミット検索を試すには履歴のあるリポジトリが必要です。別のリポジトリを試す場合も、開くのは開発用ウィンドウ側です。

### 4. 検索サーバーを起動する

1. 開発用ウィンドウのアクティビティバーにあるフクロウのアイコン <img src="../media/owl.svg" alt="OwlDiffSearchのフクロウアイコン" width="24" height="24"> をクリックして、OwlDiffSearchを開きます。見つからない場合は、コマンドパレットから `OwlDiffSearch: Open` を実行します。
2. `Setup / Start` を押します。
3. 初回はPyTorchの実行環境を選択します。表示された `Recommended` の選択肢を目安にしてください。
4. セットアップとサーバー起動が完了し、サイドバーが `Online` になるまで待ちます。

初回はPython環境の作成やパッケージの取得に時間がかかります。進捗は「表示 → 出力」の `OwlDiffSearch` で確認できます。Semantic / Hybridの初回利用時には検索モデルの読み込みやダウンロード、差分の埋め込み生成にも時間がかかります。

### 5. 検索して差分を開く

1. `Find` で `Commits` を選びます。
2. `Settings` の検索方式を `Semantic` にします。
3. 例えば `prevent duplicate searches while a request is running` のように、探したい変更内容を英語で入力します。
4. `Search` を押し、検索結果を待ちます。
5. 結果の `Open Commit Diff` を押すと、そのコミットの変更をVS Codeの差分エディタで確認できます。

初期設定では、From / Toを指定せずにHEADから直近100コミットを検索できます。上の検索文は入力例です。リポジトリの履歴によって結果は変わります。実際の変更に含まれる識別子が分かる場合は、`Keyword` でその文字列を検索して動作を確認することもできます。

### 6. 編集内容の反映と終了

TypeScriptの編集はwatchで再コンパイルされます。`Found 0 errors. Watching for file changes.` を確認したら、デバッグを再起動して変更を読み込み直します。Pythonコードを変更した場合は `Stop` → `Setup / Start` でサーバーも再起動します。

試し終わったら、サイドバーの `Stop` で検索サーバーを停止し、元のVS Codeのデバッグツールバーにある停止ボタンを押します。キーボードでは `Shift+F5`、MacでFnキーが必要な設定の場合は `Fn+Shift+F5` でも終了できます。

## VSIXを作成してインストールする

VSIXは、VS Codeに拡張機能をインストールするためのパッケージです。F5で起動せずに通常のVS Codeで使う場合は、次の手順で作成します。Windows・Mac・Linuxで同じコマンドを使用できます。

### 1. 依存パッケージをインストールする

`package.json` があるOwlDiffSearchのルートフォルダで実行します。

```sh
npm ci --include=dev
```

### 2. コンパイルしてVSIXを作成する

```sh
npm run compile
npx @vscode/vsce package
```

`npm run compile` はTypeScriptをコンパイルし、`out` フォルダに出力します。`npx @vscode/vsce package` は配布用の `.vsix` ファイルをリポジトリのルートに作成します。ファイル名にはバージョン番号が入り、例えば `owl-diff-search-0.1.0.vsix` となります。

このリポジトリではパッケージ作成時にもコンパイルが自動で実行されます。上の手順では、先にコンパイルだけを実行してエラーがないことを確認しています。

### 3. VS Codeにインストールする

1. 通常のVS Codeでコマンドパレットを開きます。Windows / Linuxは `Ctrl+Shift+P`、Macは `Cmd+Shift+P` です。
2. `Extensions: Install from VSIX...` を実行します。
3. 作成した `.vsix` ファイルを選択します。再読み込みを求められた場合は画面の案内に従ってください。
4. 検索対象のGitリポジトリを開き、OwlDiffSearchの `Setup / Start` から検索サーバーを起動します。

VSIXにはPythonの仮想環境や検索モデルは含まれません。インストール先でも、初回は `uv` を用意して `Setup / Start` を実行してください。

## 使い方

### 検索範囲の指定

- **デフォルト**: `HEAD` から遡る直近100コミットの差分を検索します（From / To の指定は不要です。履歴が100件未満なら全コミットが対象となり、作業ツリーの未コミット変更は含まれません）。
- **作業ツリーの検索**: `Settings` → `Compare range` → `When From is blank` を `Working tree / manual range` に変更し、From / To と Branch を空欄にすると 最後にコミットした状態と、現在の作業中のファイルとの差分を検索します。
- **From のみ指定**: Fromに指定したコミットより後の、HEADまでのコミットを検索します。
- **From と To の両方を指定**: Fromより後の、Toまでのコミットを検索します（From を指定した場合、100件の上限は適用されません）。
- **From が空欄で To または Branch を指定**: Toに指定したコミット、またはBranchで選んだブランチの最新コミットから、100件分の履歴を検索します。

### コミットグラフの操作

- コミット一覧は初期状態で100件読み込まれ、スクロールすると過去の履歴が追加表示されます（追加表示を行っても検索対象のコミット数は増えません）。
- コミット一覧でクリックすると `From`、Shift+クリックで `To` を選択できます。
  ブランチで絞り込み中にShift+クリックした場合は、ブランチの絞り込みを解除して選んだコミットを `To` に設定します。
- 対象範囲のコミットは緑、From は青、To は黄色でハイライトされ、ブランチラベルにはブランチごとに固定色が付きます。
- 同じコミットを指す複数のブランチやタグは「代表名 + 件数」にまとめられ、ホバーするとすべてのブランチ名とタグ名を確認できます。現在のブランチが代表名として優先され、Git の現在位置には `Current`、比較範囲の始点・終点には `From` / `To` バッジが表示されます。
- `Settings` → `Commit history` から、表示・検索対象とするブランチ、グラフに表示するブランチの数、マージされたコミットを含めるかどうかを設定できます。

### 検索単位と差分の確認

- `Hunks`: 追加・削除行および前後のコンテキスト行を含む、unified diff の個々のハンク単位で検索します。
- `Commits`: `Semantic` はファイルごとの差分の最大コサイン類似度、`BM25` はコミット内の差分をひとつの文書として評価します。`Hybrid` はこの2つを合成します。作業ツリーも1つの「Working tree changes」として扱います。`Keyword` は条件を満たした最初のファイルを検索結果に表示します。
- コミット検索の結果または青色の `Open Commit Diff` をクリックすると、そのコミットで変更された全ファイルを VS Code 標準の差分エディタでまとめて開きます（最も一致したファイルが先頭に表示され、検索フィルターで除外されたファイルも含めて変更全体を確認できます。マージコミットの場合は第1親コミットとの差分を表示します）。
- 結果内のファイル名をクリックすると、そのファイル単体の差分が開きます（`Hunks` の `Open Diff` は該当ファイル、`Branches` の `Open Best Diff` は最も一致度が高いファイルを開きます）。

### 検索モードとスコアリング

- 検索クエリは英語入力が基本です（同じ差分を再検索する際は保存済みの埋め込みが利用されます）。
- `Semantic`: クエリと差分の埋め込みを L2 正規化し、FAISS の `IndexFlatIP` でコサイン類似度を算出します。スコアは −1〜1 の範囲で小数第3位まで表示されます（候補内での再正規化は行いません）。
- `Hybrid`: コサイン類似度と、0〜1 に正規化した BM25 スコアを既定の比率（0.6 : 0.4）で合成します。
- `BM25`: Okapi BM25（`k1=1.5`, `b=0.75`）を計算し、一致した文書のスコアを min-max で0〜1に正規化してパーセント（%）で表示します。同点のみの場合は1、一致しない文書は0です。`Commits` では文書数・文書頻度・文書長・平均文書長をすべてコミット単位で計算します。対象は `Semantic` と同じフィルター済みの unified diff（ヘッダー・コンテキスト・追加削除行）で、コミットメッセージや除外ファイルは含めません。語句が一致しない場合は結果を返しません。
- `Commits` の `Hybrid` は `0.6 × ファイルごとの最大コサイン類似度 + 0.4 × コミット単位の正規化BM25` です。`Hunks` のBM25はハンクごと、`Branches` のBM25はコミット内のファイルごとに計算します。
- `Keyword`: 完全一致（Match）を表示します。
- 旧形式の L2 インデックスは、保存済みの埋め込みからコサイン検索用へ自動変換されるため、埋め込みの再計算や手動でのキャッシュ削除は不要です。
- プログラミング言語の選択は不要です。サイドバーの言語表示は参考情報であり、依存関係ファイル、ロックファイル、YAML、拡張子のないファイルも検索できます。Markdown などのドキュメント類はデフォルトで除外されますが、設定から対象に含めることも可能です。

### クエリの記述例

自然言語で探すときは `Semantic` を選び、「何に対して、どんな動作を追加・修正したか」を簡潔な英語で入力します。

| 探したい変更内容 | 入力例 |
|---|---|
| 必須項目がないリクエストを拒否する | `reject requests with missing required fields` |
| タイムアウトしたリクエストを再試行する | `retry requests after a timeout` |
| 認証トークンをログに出さないようにする | `redact authentication tokens from logs` |
| 入力が変わっていない場合にキャッシュを再利用する | `reuse cached results when the input has not changed` |
| 検索処理中の重複リクエスト（連打）を防ぐ | `prevent duplicate searches while a request is running` |
| テストコード内のプライベートAPIを公開APIに置き換える | `replace private test helpers with public APIs` |

- **検索文を書くときのコツ**: 1つのクエリには1つの具体的な変更内容を記述します。例えば単に `fix bug` とするのではなく、「どんな状況で何を防ぐか」を補足して `avoid crashing when the response body is empty` のように記述します。
- 関数名、エラーメッセージ、HTTP メソッドなどの具体的なキーワードが分かっている場合は、クエリに含めるか `BM25` / `Keyword` モードを利用すると効果的です。
- 探したいものに合わせて、コミットを探すなら `Commits`、個々の差分箇所なら `Hunks`、変更を含むブランチなら `Branches` を選択してください。

### 検索対象の絞り込み（フィルター）

`Settings` → `Target filters` から、リポジトリルートを基準としたパスまたは glob パターンをカンマ区切りで指定できます。

- `Include .py`: Python ファイルのみ
- `Include src/**`: `src` ディレクトリ配下のみ
- `Include src/**/*.py`: `src` ディレクトリ配下の Python ファイルのみ
- `Include src/app.py`: 特定のファイルのみ
- `Exclude tests/**, docs/**`: テストとドキュメントを除外
- `Exclude documentation files`: `.md`、`.rst`、`.adoc`、`.org` などのドキュメントや、拡張子のない `README`、`CHANGELOG`、`LICENSE` などを除外（デフォルトでオン）

> **補足**:
> - `Include` を複数指定した場合は、いずれかに一致するファイルが対象になります（OR 条件）。
> - `Exclude` およびドキュメント除外設定は、`Include` の結果からさらに除外されます。
> - `Commits` 検索では、条件に一致するファイルを含むコミットのみが抽出され、一致したファイルの差分だけが検索対象となります。
> - ドキュメント除外をオフにし、`Include` / `Exclude` を空欄にすると、すべてのテキスト差分を検索します。なお、`package.json` や `requirements.txt` などの依存定義ファイルは、ドキュメント除外がオンのままでも検索対象に残ります。

### ブランチとマージ履歴の絞り込み

`Settings` → `Commit history` で、対象ブランチや履歴の遡り方を指定できます（From / To を直接入力する場合は、同じく Settings 内の `Compare range` で設定します）。

- `Branch`: 特定の1ブランチのみに絞り込みます。ここで選択したブランチは To の指定より優先され、コミットツリーと差分検索の両方に適用されます。
- `Max branches`: `All visible branches` 選択時、グラフに表示するブランチの数を制限します。更新日時が新しいブランチから表示します（現在のブランチは常に最優先されます）。
- `Full history`: マージコミットのすべての親コミット（parent）を遡ります。通常のフィーチャーブランチのマージで複数コミットがある場合、それらの個別コミットもツリーおよび検索対象に含まれます。
- `First parent`: 選択したブランチのメインライン（第1親）のみを辿ります。フィーチャーブランチ側の個別コミットは辿らず、取り込まれた変更全体をマージコミットの差分として扱います。

※ Fast-forward マージや Rebase を行った場合は、個々のコミットが直線的な履歴として残ります。Squash マージの場合は元の個別コミットは統合されず、1つの squash コミットのみが対象となります。

### 変更内容からブランチを探す（Branches モード）

1. 画面上部の `Find` で `Branches` を選択します。
2. `Changes not in` で検索の基準にするブランチ（例: `main`）を選択します。`Auto` を選ぶと、ローカルの `main`、`origin/HEAD` が指すブランチ、`master` などから自動選択されます（判定できない場合は手動で指定してください）。
3. 検索ボックスに探したい変更内容（例: `retry failed authentication`）を入力して検索します（日本語翻訳を有効にしている場合は日本語での検索も可能です）。
4. 変更内容との関連度順にブランチ名が表示されます。`Matching changes` に表示されたコミットをクリックすると根拠となったファイル差分が開き、`Open Best Diff` で最も一致度が高いファイル差分を直接開くことができます。

**仕様と注意点**:

- 検索対象はローカルブランチおよび取得済みのリモート追跡ブランチです。各ブランチのうち、基準に選んだブランチには含まれていないコミットを検索します。ファイルごとに差分を評価し、その中で最も高いスコアをブランチのスコアにします（`Keyword` モードでは一致したブランチが名前順で表示されます）。
- 結果には、検索に一致したコミットが最大3件まで表示されます。なお、ブランチ名やコミットメッセージ自体は検索スコアには影響しません。
- 同じコミットを含む複数ブランチが存在する場合、検索用の埋め込みは共有されます。ローカルブランチと追跡ブランチが同じコミットを指している場合は、エイリアス（別名）として1つの結果にまとめられます。
- `Include` / `Exclude` フィルターはブランチ検索にも適用されます。
- `Branches` モードではすべてのブランチを検索するため、ツリー表示用の `Branch`、`Max branches`、`History` や From / To の範囲指定は無視されます（マージで取り込まれたコミットも検索します）。
- 検索処理によってリポジトリの checkout や fetch が勝手に行われることはありません。
- 基準のブランチにすべてのコミットが取り込まれたブランチや、削除されたブランチは結果に表示されません。ただし、Squash や Rebase によってマージされた場合はコミットハッシュが異なるため、同一の変更であっても元ブランチが結果に残る場合があります。

### 検索処理の制御とキャッシュ

- **二重リクエスト防止とキャンセル**: 検索実行中は Search ボタンの連打や Enter キーによる二重送信が防止されます。検索文、基準のブランチ、検索対象、ファイルの絞り込みなどを変更すると以前の結果は自動でクリアされ、新しい条件での検索が即座に優先されます（遅れて届いた変更前の結果や翻訳、エラーが表示されることはありません）。同時にリクエストが発生した場合は順番に処理され、実行中も進捗確認やキャンセル操作を受け付けます。
- **埋め込みキャッシュの仕組み**: 生成された埋め込みベクトルは、差分テキストの内容とモデル設定をキーとして保存されます。そのため、新しいコミットを追加した後やサーバーを再起動した後でも、既存の差分に対する埋め込みはそのまま再利用されます。検索範囲やフィルター条件、検索単位を変更しても、モデルに渡す差分テキストが同一であれば再計算は行われません。検索ステータスには `2 reused / 1 new embeddings` のように再利用数と新規計算数が表示されます。なお、キャッシュは `Clear Cache` ボタンからいつでも削除できます。

## Geminiによる翻訳・クエリ拡張

> **日本語クエリの英訳機能を利用する場合**:
> VS Code の設定で `owlDiffSearch.geminiApiKey` に API キーを設定し、サイドバーの `Settings` → `Gemini query preparation` で `Translate JP → EN with Gemini` または `Expand query with Gemini` を有効にしてください。

- クエリ拡張の設定は `owlDiffSearch.enableQueryExpansion`（既定は無効）です。英語・日本語の両方に対応し、翻訳と拡張を両方有効にしてもGeminiへのリクエストは1回です。`Keyword` は元の入力をそのまま使います。
- `Semantic` / `Hybrid` では機能や変更内容を説明する文章を、`BM25` では技術用語や関連する語句を中心にした短い検索文を生成します。NightOwl使用時は、[モデルカード](https://huggingface.co/Shuu12121/NightOwl-CodeEmbedding) に記載されたコードと自然言語コメント、変更意図と差分の学習を指示に含め、docstringのような簡潔な説明に整えます。別の埋め込みモデルにはこの指示を付けません。
- 生成した検索文は結果の上に `Expanded query` として表示され、入力欄の原文は保持されます。APIキー未設定・通信エラー・空の応答の場合は通知し、元の入力で検索します。Geminiへ送る内容は検索クエリと検索方式の指示です。
- このリポジトリの翻訳と拡張の既定モデルは `gemini-3.8-flash` です。モデル選択は両機能で共通です。既に旧モデルを明示設定している場合は、サイドバーまたは `owlDiffSearch.geminiModel` で変更してください。

### Agentic検索

APIキーを設定したうえで、`Settings` → `Gemini query preparation` → `Agentic search with Gemini` を有効にしてください（`owlDiffSearch.enableAgenticSearch`、既定は無効）。入力した目的からGeminiが検索クエリを作り、結果を読んで追加検索・終了を判断します。英語・日本語入力と `Hunks` / `Commits` / `Branches` に対応しています。

- 最初は選択中の検索方式を優先し、その後は `Semantic` / `Hybrid` / `BM25` / `Keyword` をGeminiが選択できます。検索対象・ファイルフィルター・ブランチ・コミット範囲はすべての検索で固定します。
- Geminiには Function Calling の `search_diff`（意味・Hybrid・BM25検索）、`keyword_search`（文字列の確認）、`finish_search` を渡します。Geminiが `keyword_search` を呼ぶとローカルサーバーで実際に検索し、ヒットした差分の行と前後の文脈をツール応答として返します。例えば意味検索で見つけた `validate_session` を追加検索し、その実結果を読んでから判断できます。
- `keyword_search` は選択範囲の差分を対象に、大文字・小文字を区別せず、空白で区切った全語が同じ検索単位に含まれるか確認します。正規表現やOR構文には対応しません。0件もそのままGeminiへ返します。文脈行や削除行も対象なので、現在のソース全体での有無や動作を証明するものではありません。
- キーワード確認も検索回数の上限に含みます。結果カードの `Keyword hits` で実際にヒットした行を確認できます。`Diff line` は差分内の行番号です。ヒット箇所の抜粋は1候補あたり最大3か所で、長い差分の先頭以外も確認できます。
- 翻訳・クエリ拡張の設定よりAgentic検索が優先されます。通常の `Keyword` と異なり、Agentic検索ではクエリや検索方式の変更が可能です。
- 検索回数は既定3回、`owlDiffSearch.agenticMaxSearches` で1〜6回に変更できます。Gemini呼び出しは通常「検索上限＋最終確認1回」までで、一時的な通信障害・タイムアウト・不正なツール応答からの復旧に限り最大2回追加します。同じクエリと検索方式の繰り返しは停止します。
- Geminiへ検索目的・実行履歴・検索結果のタイトル・パス・コミットID・差分の一部を送信します。検索ツールの応答は最大10件、比較・評価に使う検索結果の一覧は最大30件で、通常の差分の抜粋は1件あたり最大1,800文字です。キーワード検索では一致箇所の抜粋を返し、後続の判断にもツール呼び出しと応答の履歴を渡します。コメントや差分の内容は判断用データとして扱い、ファイルの変更やシェル実行は行いません。
- 結果の上に検索クエリ、方式、件数、短い検索目的と終了時の説明を表示します。複数検索の候補は重複を除き、各検索内の順位を使う Reciprocal Rank Fusion（`Σ 1/(60 + 順位)`）で統合します。Geminiは終了時に各候補の関連度（0〜100）、修正内容の一文要約、関連すると判断した理由を返します。要約と理由は入力クエリの言語で記述します。
- Agentic検索結果は既定で `Relevance (Gemini)` の関連度順に表示します。`Sort results` を `Search ranking` に切り替えると複数回の検索順位をRRFでまとめた順に表示します。切り替え時の追加検索・Gemini呼び出しはありません。通常検索の順位は変更しません。
- `Relevance 85/100` のような表示は、検索で取得した差分に基づくGeminiの評価であり、確率やコサイン類似度ではありません。評価がない候補は `Not assessed` と表示し、関連度順では評価済み候補の後ろに置きます。根拠不足の場合は要約・理由にその旨を記載させ、未確認の修正内容や関連度を補いません。
- 評価の文章が長い場合は表示用に短縮し、数値文字列や小数の関連度は0〜100の整数へ整えます。無効な評価や、検索で取得していない候補への評価は、その項目だけを除外し、他の評価を保持します。除外した場合は検索履歴に注記します。
- Geminiの応答待ちは1回90秒です。応答が途中で切れた場合は短い最終評価を求め、不正なツール引数はGeminiへ返して修正を求めます。停止時はタイムアウト、HTTPステータス、検索ツールの応答の問題などを検索履歴の `Diagnostics` とVS CodeのOwlDiffSearch出力へ記録します。APIキーや応答本文はログに出しません。利用枠・頻度制限（HTTP 429）は自動再試行しません。
- `Cancel` で停止できます。検索条件を変更したときも進行中の検索を中断し、古い結果を表示しません。途中で停止・エラーになった場合は取得済みの結果を残します。初回のGemini判断が失敗した場合は元の入力で通常検索を1回行います。

## 起動や検索で困ったとき

| 状況 | 確認すること |
|---|---|
| F5で拡張機能が起動しない | 元のウィンドウでOwlDiffSearchのルートを開き、起動構成が `Run Extension` になっているか確認します。 |
| `tsc` が見つからない／SDKの型定義でコンパイルエラーになる | ルートで `npm ci --include=dev` を実行し、`npm run compile` で確認します。 |
| `uv` が見つからない | uvをインストールし、ターミナルで `uv --version` を確認します。インストール後はVS Codeを再起動します。 |
| `Offline` のままになる | 出力パネルの `OwlDiffSearch` とエラー通知を確認します。初回セットアップが完了しているかも確認してください。 |
| 結果が出ない | 開発用ウィンドウで開いているフォルダ、Git履歴、From / To、Branch、Include / Exclude、ドキュメント除外を確認します。 |
| 変更が画面に反映されない | watchのコンパイル完了を確認し、デバッグを再起動します。Pythonの変更ならサーバーも再起動します。 |

## ビルドとテスト

OwlDiffSearchのルートで実行します。

```powershell
npm run compile
npm run lint
npm test
npm run test:extension
```

`npm test` はコンパイル・Lintの後にNode.jsのテストを実行します。`npm run test:extension` はVS Code / Electronを起動できる環境が必要です。

セットアップ済みのPython環境でサーバー側をテストする場合（Windows）:

```powershell
cd model_server
.venv/Scripts/python.exe -m unittest discover -s tests
```

macOS / Linuxでは、Pythonの実行パスを `.venv/bin/python` に読み替えてください。

依存関係は `package.json` と `package-lock.json` で管理しています。Gemini SDKの型定義が参照する `@modelcontextprotocol/sdk` は開発依存に含め、Mocha配下の `serialize-javascript` にはoverrideを設定しています。
